# Codexの実装のレビュー（REFRESH）

Claude Code はこのリポジトリでゲームのコードを書かない。役目は、Codexの実装が仕様どおりか、ゲームとして良くなっているかを確かめて、ユーザーに分かる言葉で伝えること。

引数：PR番号（例：`5`）。なければユーザーに番号を聞くか、開いているPRの一覧から、Codexのもの（ブランチ名が `codex/`）を選ぶ。

## 1. 読む（毎回）
1. `docs/企画メモ.md`（正本）。特に「決定」と「不採用」
2. PRの本文と変更ファイルの一覧（GitHubのツールで `get`。差分が大きいときは手元に取り込んで見る）
3. PRが扱う段階の仕様：`docs/spec.md` の 10.2（作る順番）でその段階の中身と「確認すること」を見て、関係する4章・5章の節を読む
4. `docs/デザインの決まり.md`、`AGENTS.md` の「必ず守ること」
5. `docs/実装メモ.md` の先頭（Codexが今回仮に決めたことと見本との差）

## 2. 手元で動かす
作業用ブランチを汚さないよう、スクラッチパッドに別の作業場所を作る。

```bash
git fetch origin <PRのブランチ> main
git worktree add <スクラッチパッド>/pr<番号> origin/<PRのブランチ>
cd <スクラッチパッド>/pr<番号>/game && npm ci && npx vitest run && npm run build
```

- テストの件数とビルドの大きさが、PRの本文に書かれた数と合うか
- 終わったら `git worktree remove --force <スクラッチパッド>/pr<番号>` で片付ける

## 3. 画面を撮って見本と比べる
- 状態の一覧は、PRのブランチの `README.md` の `?state=` の節（新しい段階の状態は `fixtures.ts` の `FIXTURE_NAMES`）
- 撮影：`node .claude/skills/review-pr/shots.js <作業場所>/game/dist/index.html <スクラッチパッド>/shots <状態名...>`
  （日本語・英語 × 1920×1080・1366×768。`LOCALES`・`SIZES` で絞れる）
- 見本：`node .claude/skills/review-pr/mockup.js docs/mockups/<番号>-*.html <スクラッチパッド>/shots/mock.png`
- 画像を実際に開いて見る。見るところ：
  - 見本との構図・寸法・文字の大きさの違い
  - 文字のはみ出し・重なり・不自然な改行、別の言語の混入
  - `docs/デザインの決まり.md` の「避けること」（大きな角丸・ふんわりした影・カプセル形の札・鮮やかな青と紫 など）
  - さわれない飾り、未解放のものを見せすぎていないか（「次の1つ」だけ）
  - 本物のWindowsのアプリならどうなっているか（日時・件数・アイコンの出し方など）
- 小窓やメニューは、Playwrightで実際に押して開いた状態も撮る

## 4. 中身を確かめる
差分を読み、特に次を見る。疑わしいものは、一時的なテストやスクリプトで**実際に測って**から書く（推測だけで指摘しない）。

- 仕様どおりか：数式、条件、上限、解放の順番、報酬の重複防止
- 保存データ：大きさ（ブラウザの保存の上限は約5MB。本体と予備の2つを持つ）と、保存1回にかかる時間。長く遊んだ状態（上限まで溜めた状態）でも測る
- 古い保存データとの互換：今の形式を変えたときに、古いデータが読めなくなる作りになっていないか。次の段階で形式が変わる予定なら特に
- 遊び心地：同じ依頼の繰り返し、待ち時間、押しても何も起きないボタン
- 数値は仮なので、細かい値の調整は指摘しない（目標時間から大きく外れるときだけ）

## 5. ユーザーへの報告（チャット）
`CLAUDE.md` の「ユーザーとの進め方」に従い、平易な日本語で、専門用語とコードの話を避ける。並べ方：

1. ひとことの結論（次の段階に進んでよいか、先に直すものがあるか）
2. よくできている点（短く）
3. 次の段階の前に直してほしいこと：何が起きるか、測った数値、直し方の案
4. 小さな点（ついでに直せば十分なもの）
5. 見本との違いでユーザーが決めること：Codexが実装メモに理由を書いたもの。決めてほしいことは1〜2個に絞る

最後に「Codex向けのコメントとしてPRに書き込むか」を聞く。**ユーザーが了承するまで書き込まない。**

## 6. PRへのコメント（ユーザーが了承したら）
- Codexが会話を知らなくても直せるように、ファイル名・関数名・測定の結果・直し方の案を書く（こちらは技術的に書いてよい）
- 見出しは「必須（次の段階の前に）」「小さな点」「確認のお願い」
- ユーザーがまだ決めていない見本との違いは、変更の依頼に入れない（提案を決定として扱わない）
- 最後に、決められた署名の行（`Generated by Claude Code`）を付ける
- 書き込んだら、そのURLと、入れたもの・入れなかったものをユーザーに伝える

## しないこと
- PRのブランチへのコミットや push（直すのはCodex）
- 承認やマージ（`main` に入れるかはユーザーが決める）
- `docs/handoff/` の編集
