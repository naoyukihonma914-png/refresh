## 1. このゲームで一番実現したい体験

最初は、無機質なテキストだけの画面に「ピクセルを1つ生成する」というボタンが一つある。クリックして集めたピクセルで、枠線、色、フォント、動き、自動クリック用カーソル、ウィンドウなどを作る。

買ったアップグレードは数字だけを増やすのではなく、**今、自分が操作しているゲーム画面そのものを変える**。画面を使って画面を育て、自分でUIや機能をクラフトしている感覚がほしい。

最初の依頼では「ゲーム画面の構成要素そのものをリソースとして消費・拡張していく抽象インクリメンタル」と表現しました。単なる見た目の着せ替えに留まらない発想です。ただし、既存UIを取り壊して素材にするのか、どんな部品を何に変換するのかといった具体的な消費・再利用のルールは、まだ確定していません。

その気持ちよさを序盤だけで終わらせず、最後まで続けたい。世界が色づき、精細になり、豪華になり、新しいスケールへ広がっていくことを、見た目と操作の両方で実感したい。

アプリが増えるだけ、数値が増えるだけ、同じ白い管理画面のパネル数が増えるだけでは物足りない。節目では、それまでの世界がより大きな世界の一部だったと分かるような、**「ガラッと新世界に突入する」変化**がほしい。

> やはりウィンドウだけだと視覚的な変化に限りがありますね。さっきの話みたいにアプリになっていったりなどとにかく視覚的な変化や豪華さをひたすらに与えながらスケールが上がっていく感じにしたいですね

> 正直4～6の段階に視覚的な大きな差を感じませんね。全体的にデザインを考えなおした方がいいかも、MACのOSのような視覚的にとっつきやすい見た目にもしたいですね。

> 現状だとAIが作った感満載のUIの見た目に細かい文字や数字、AI特有のキャッチコピー的な短文が散りばめている感じもします。フォントや見た目にもっと気を使ってみて。

> 現状は抽象度の高いただのアプリやデスクトップのようなUIなだけなので、みるからにリアル感のある各画面を高いクオリティで作成して、まるでゲーム内ではなく実際のPCと錯覚するような具体性をもったデザインにして

「4～6」は当時の試作の段階番号への批評であり、最終版を同じ段階数・構成に固定する指定ではありません。

| 具体的なPCらしさ | 用途が分かる画面、文書、ファイル、ツール、状態、操作反応などを持たせる。意味のない装飾パネルで埋めない。 |

上記は既に伝えた方向性です。ただし今後、私が明示的に変更した場合は新しい発言を優先してください。

### 解釈を間違えてほしくない点

- 「リアルなPCらしさ」は、物理的なPC本体を描くことではなく、**画面内のソフトウェアに具体性と説得力を持たせること**です。
- 写真壁紙の中に風景があることと、ゲームの舞台が画面外の机へ移ることは別です。現試作には風景壁紙があります。
- 「Macのように」は仕上げや親しみやすさの参考です。三色ボタンなどの模倣を求めていません。
- 全画面を変化させたいのであって、資源量や購入先を隠して操作しにくくしたいわけではありません。世界との一体感と分かりやすさを両立したいです。
- 色数や発光量を際限なく増やすだけで「豪華さ」を表現する方針には、まだ合意していません。
- 後半を仮想環境管理やネットワーク管理にすることは、現在の試作で採った案です。最終仕様として承認済みではありません。

## 4. 元のゲーム：どこが好きで、どこを変えたいか

元資料は `ui-alchemist.html` と `UIアルケミスト_ゲーム概要.md` です。補足ZIP内の `original/` に、変更せずコピーしてあります。

### 元の進行

1. **テキスト期**：生成ボタン一つから、枠線、セーブ機能、色、キーボード入力、フォント、アニメーションなどを錬成。カーソルがボタンの周囲を動いて自動で押す。
2. **ウィンドウ期**：6×4マスの `main.ui` にボタン、スライダー、グラフ、ターミナルなどのモジュールを配置。隣接効果を考えて限られた面積を使う。満杯になると枠が揺れ、「フレーム破壊」を錬成できる。
3. **回路期**：ウィンドウの枠が砕け、回路平面へ移る。ノードの配線、コアへの接続、閉じたループの倍率などを扱う。
4. **空間期**：回路が3Dワイヤーフレーム空間になり、高さ・レイヤー複製で生産を伸ばし、次元の境界で終了。

私は、**最初の画面からウィンドウを破壊するところまではとても気に入っていました。その後の回路・空間への方向は気に入っていませんでした。**

「ウィンドウを破壊した後も、最後までUIを創造していたい」が出発点です。元ゲームを丸ごと否定しているわけではありません。また、元ゲームの前半を一切変えずにそのまま使うと確定したわけでもありません。

### 元ゲームに存在した仕組み（参考・再採用未決定）

| 仕組み | 元ゲームでの内容 |
|---|---|
| モジュール配置 | 限られたマスに生産部品を置く。置き換えと配置のパズルがある。 |
| 隣接支援 | コア、アンプ、ミラー、ルーターなどで周囲の出力に影響する。 |
| 古い部品のシナジー | 下位部品の所持数が上位部品の出力に影響し、古いものにも役割が残る。 |
| 段階的開示 | 次の要素を少しずつ見せる。統計などの機能も錬成対象になる。 |
| アクティブ操作 | 連打による熱、バグ捕獲、短時間のオーバークロック。 |
| 放置 | オフライン生産は最大12時間。 |
| 転生 | リファクタリングで圧縮コードを獲得。恒久倍率とライブラリで次周を変える。 |

これらは**元資料の記述**であり、今回の新作への採用指示ではありません。特に回路、3D、転生の復活を、資料に書いてあるという理由だけで前提にしないでください。

元資料の自動プレイ試算はエンディング約60分、人が遊ぶと1.5～2倍程度という想定でした。一方、元資料自身にウィンドウ期の短さ、後半の急加速、転生後の短すぎる周回が課題として挙がっています。今回の目標時間は未決定です。

### 実装済みの操作・仕組み

- 生成、ピクセル消費による順番固定の27アップグレード、カーソルの追加。
- 自動生成、手動／自動の配分変更、20秒ごとのゲージ報酬、後半のカーソル自動購入。
- 生成・購入・所持量はアプリやOS内に組み込んでいる。外側に常設ゲーム用サイドバーはない。
- 全画面の切替時、前の画面を縮めて次の画面の内側に収める遷移演出。
- デスクトップ上のウィンドウ移動、最小化、復帰、最大化、前面化。
- ファイル一覧、編集できる「制作ノート.txt」、写真閲覧、設定。
- Canvasのツール選択、レイヤー選択、写真切替、限定的なズーム。
- 内包している環境を開いて操作し、外側へ戻る操作。
- ローカル自動保存、セーブのJSON書き出し・読み込み、不在生産最大8時間、任意の効果音。
- 既存OSの三色ボタンやロゴを使わず、画面内だけで完結する。
- 段階別プレビュー。本編のセーブを変更せずに比較できる。

### 実装の限界・未実装

- 基本の進行は「資源を貯め、決まった次のアップグレードを買う」もの。自由な組立や分岐を主軸にしたゲームにはまだなっていない。
- 元ゲームにあった6×4マスの配置、隣接効果、モジュール合成、回収、転生などは最新試作にない。
- Canvasはフル機能のデザインソフトではない。ツールの一部は選択表示だけで、自由に文書を作れるわけではない。
- ファイル管理やタスクバーなど、一部は説明上の解放より先に画面に存在する。機能をクラフトした手応えとの整合は改善余地がある。
- 環境は再帰的に表示しているが、小さな内側プレビューを常時直接操作する作りではない。明示的に環境を開いて操作する。
- 実際のOS、ファイルシステム、ネットワークPCとは接続しない。ブラウザ内のシミュレーション。
- 自動操作の試算では約693秒で最後まで到達する。これは現在の仮バランスであり、希望する完成版の長さではない。
- 「待つだけにしない」「以前の成果を失わない」「配置や合成を入れる」「転生を入れる」などの詳細は、これから相談できる。これら全部に私が採用合意したわけではない。

## 7. これから一緒に決めたいこと

**私は、まだ話していない追加要素をたくさん持っています。以下の検討項目だけで議論を閉じず、まずそれを聞いてください。** 以下は整理に使う論点であり、採用済み機能ではありません。

### ゲームの中心となる行動

- クリック、生産、購入以外に、何を繰り返すことが楽しいゲームにするか。
- 部品を置く、組み合わせる、つなぐ、編集する、再利用する、といった行動をどこまで持たせるか。
- 自由な創作と、少しずつ見た目が完成していく達成感をどう両立するか。
- UIの見た目のカスタマイズと、生産上の戦略をどう結び付けるか。
- 古い部品や前の世界に、進行後もどんな意味を持たせるか。

### 進行と視覚変化

- 前半から終盤まで、どの世界をどんな順序で作るか。
- 段階間で「何が内包され、どの視点が変わり、どんな操作が新しくなるか」。
- 各段階の中にも、小さな変化の頻度と大きな変化の節目をどう作るか。
- 白、青、暗色といった色替え以外に、構図、密度、素材、タイポグラフィ、動きをどう変えるか。
- 縮小プレビューと管理画面の反復だけに頼らず、画面内でどこまで新世界を表現できるか。
- 完成時の画面をどう見せ、何をもって「作り上げた」と感じさせるか。

### 遊ぶ時間と継続

- 1回のプレイ時間、エンディングまでの時間、長期的な遊びをどう想定するか。
- アクティブ操作と放置の比率、行き詰まりや待ち時間をどう設計するか。
- 転生・周回を採用するか。採用するなら、何を失い、何を残し、見た目に何が増えるか。
- 再プレイで同じ見た目をやり直すことが、今回の狙いに合うか。

### 操作と制作範囲

- 「本物のPCらしい」操作として何を実際にできるようにし、どこを演出に留めるか。

## 8. 仕様を決めるときの整理方法

私から出る案とあなたの提案は、まず次の状態に分けてください。

| 状態 | 扱い |
|---|---|
| 必須 | 私が明示的に採用した、完成版に必要なもの。 |
| 試して判断 | 短い試作や見本で体験を確認してから決めるもの。 |
| 将来候補 | 今回の完成に必須ではないが残しておくもの。 |
| 不採用 | 理由を記録し、同じ案を無自覚に戻さないもの。 |
| 未決定 | まだ回答や合意がないもの。推測で埋めない。 |

各機能について、「何ができるか」だけでなく、次も具体化してください。

1. どんな楽しさ・視覚的報酬を生むのか。
2. いつ、何を条件に解放されるのか。
3. プレイヤーは画面のどこを、どんな順番で操作するのか。
4. 何を消費し、何が生成・変更されるのか。
5. 操作前後で画面がどう変わるのか。
6. 生産や他の機能とどう関わるのか。
7. 次の世界へ進んだ後、何が残り、どう使えるのか。

視覚面は「豪華」「洗練」「没入感がある」だけで済ませず、画面全体の構図、色の面積、主役、文字の大きさ、素材、動き、遷移前後を説明してください。必要なら見本で比較したいです。

## 9. 最終的にCodexへ渡したい仕様書

議論がまとまったら、少なくとも以下を含む、単独で読める文書にしてください。

1. **狙いと判断基準**：このゲームの楽しさ、必ず守ること、避けること。
2. **全体の進行表**：各段階の入口・出口、行動、資源、画面の特徴、前の世界との関係。
3. **基本ループと経済**：生産、消費、選択、増幅、解放の関係。未調整の数値は仮値と明示。
4. **個別ギミック**：操作、状態、成功・失敗、報酬、相互作用、保存対象。
5. **画面仕様**：全画面の構図、主要操作、文字、配色、素材、遷移、内包した世界の扱い。
6. **最初のプレイ体験**：開始から最初の大きなスケールアップまでの具体的な流れ。
7. **中盤・終盤・完成**：新しさをどう維持し、何を達成して終えるか。
8. **時間の設計**：アクティブ／放置／不在、目標時間、周回の有無。
9. **データと例外**：セーブ、復元、旧試作データ、リセット、タブ復帰、画面サイズ変更。
10. **実装計画**：最初に遊べる短い完成区間、確認点、その後の拡張順。現行コードの再利用方針。
11. **受け入れ条件**：どの画面・操作・変化が実現すれば、その機能の完成と判断できるか。
12. **未決定・保留・不採用一覧**：理由と、決めるために必要な検証。

仕様確定前に、全部の価格や倍率まで厳密に決める必要はありません。ただし、ゲームの軸・操作・進行・見た目の大きな構造が曖昧なまま、「あとはよしなに実装」とはしたくありません。

### 視覚面の確認基準として使いたいこと

以下は既出要望を確認可能にするための整理案で、未合意の数値基準を新設するものではありません。

- 段階名や説明を隠して並べても、前後の世界の違いが伝わるか。
- 色だけでなく、画面の構成と操作の規模も変わっているか。
- 大きな節目で、前の世界がどこに収まったか分かるか。
- 新しく作ったUIが、実際の操作や生産に使われているか。
- 資源・生成・購入が世界の中で自然に理解できるか。
- 小さな文字や意味のない数字で画面を埋めていないか。
- 序盤の小さな変化と後半の大きな変化が、どちらも気持ちよいか。
